# Регрессия при BUCKET_CHUNK_SIZE=5

**Дата:** 2026-07-24

## Эксперимент: Увеличение BUCKET_CHUNK_SIZE с 1 до 5

### Гипотеза
Более агрессивная агрегация (группировка секций по 5 вместо 1) должна:
- Уменьшить количество переменных
- Ускорить решение
- Сохранить или улучшить качество

### Изменения
```python
# solver/cp_sat_aggregated.py:82
_BUCKET_CHUNK_SIZE = 5  # Было: 1
```

## Анализ причин

### 1. Рост NARROW_AISLE_MISMATCH (+91 паллета)

**Это ключевая проблема.** Увеличение с 64 до 155 показывает, что узкопроходные паллеты перестали размещаться правильно.

**Возможные причины:**

#### a) Потеря точности при бакетировании

При `BUCKET_CHUNK_SIZE=5` одна группа физически одинаковых секций режется на чанки по 5:
```
[sec1, sec2, sec3, sec4, sec5] → bucket_0
[sec6, sec7, sec8, sec9, sec10] → bucket_1
...
```

Агрегированная модель видит Y[ptype, bucket_0] и Y[ptype, bucket_1] как независимые переменные.

**Проблема:** Дезагрегация может неправильно распределять паллеты внутри бакета из 5 секций:
- Агрегированное решение: "разместить 3 паллеты типа X в bucket_0 (5 секций)"
- Дезагрегация: выбирает первые 3 секции жадно, но они могут быть неподходящими

#### b) Ограничения width/weight/slots для бакета из 5 секций

При `BUCKET_CHUNK_SIZE=1` каждая секция = отдельный бакет:
```python
total_width = remaining_width * 1  # Точное значение для одной секции
```

При `BUCKET_CHUNK_SIZE=5`:
```python
total_width = remaining_width * 5  # Суммарная ширина 5 секций
```

CP-SAT solver видит суммарное ограничение и может распределить паллеты так, что при дезагрегации не хватит места в конкретных секциях.

#### c) Узкопроходные секции + strict режим

При `strictNarrowAislePlacement=True` узкопроходные паллеты строго в узкопроходные секции.

**Если** узкопроходных секций мало (например 50-100 из 1530), и они сгруппированы в бакеты по 5:
- Агрегированная модель видит ~10-20 узкопроходных бакетов
- Огрубление приводит к переоценке вместимости
- Дезагрегация не может разместить все паллеты

### 2. Рост времени выполнения (+59s)

Парадокс: меньше переменных → дольше работа?

**Объяснение:** Solver нашёл худшее решение (FEASIBLE, не OPTIMAL) быстрее, но постобработка (residual solving) пыталась дорешить больше паллет (292 vs 167) → больше времени на дезагрегацию.

## Вывод

❌ **BUCKET_CHUNK_SIZE=5 НЕ РАБОТАЕТ для задачи с узкопроходными ограничениями.**

✅ **BUCKET_CHUNK_SIZE=1 остаётся оптимальным** — каждая секция = отдельный бакет, точность максимальна.

## Рекомендации

### Вариант A: Адаптивный BUCKET_CHUNK_SIZE

```python
# Для узкопроходных секций: BUCKET=1 (точность важнее скорости)
# Для обычных секций: BUCKET=3-5 (скорость важнее)
if key[5]:  # narrow_aisle
    chunk_size = 1
else:
    chunk_size = 5
```

### Вариант B: Улучшенная дезагрегация

Текущая дезагрегация жадная — выбирает первую подходящую секцию из бакета.

**Улучшение:** При дезагрегации бакета из N секций использовать мини-solver для точного распределения паллет.

### Вариант C: Сохранить BUCKET_CHUNK_SIZE=1

Простое и работающее решение. Агрегация по типам уже сократила переменные с 2.35M до ~1000 — этого достаточно.
