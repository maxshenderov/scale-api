# Идея: Параллельное решение для узкопроходных и обычных паллет

## Концепция

Разделить задачу размещения на два независимых подмножества:

1. **Narrow task:** `is_narrow` паллеты → `narrow_aisle` секции
2. **Wide task:** остальные паллеты → остальные секции

Каждая задача решается отдельным CP-SAT solver, результаты объединяются.

---

## Преимущества

✅ **Параллелизм:** Два solver работают одновременно → потенциально 2× ускорение  
✅ **Меньше переменных:** Каждая задача проще → быстрее достижение OPTIMAL  
✅ **Естественное разделение:** Физически узкопроходные паллеты ограничены своими секциями

---

## Проблемы и риски

### 1. Конфликт с `strictNarrowAislePlacement=false`

**Текущая логика (default):**
```python
# api/schemas.py:142
strictNarrowAislePlacement: bool = True  # По умолчанию
```

**Но** в S7 тесте:
```python
# tests/test_s7_vs_standard.py:41
S7_SETTINGS = OptimizationSettingsSchema(
    allowReslot=False,
    maxOperations=5000,
    timeLimitSeconds=180,
    # strictNarrowAislePlacement НЕ указан → используется default=True
)
```

**Значит:** S7 использует `strictNarrowAislePlacement=True` → узкопроходные паллеты строго в узкопроходные секции.

**Вывод:** ✅ Для S7 разделение корректно — никакого cross-placement не происходит.

### 2. Existing pallets и реслот

При `allowReslot=True` существующие паллеты могут перемещаться. Если узкопроходная паллета сейчас в обычной секции, разделение задачи сломает логику:
- Narrow task не увидит текущую секцию паллеты (она в Wide task)
- Wide task не может двигать узкопроходную паллету

**Для S7:** `allowReslot=False` + `existing=0` (холодный старт) → этой проблемы нет.

### 3. Неравномерная нагрузка

Если узкопроходных паллет мало (например 64 из 3406 = 1.9%), narrow task решится за секунды, а wide task будет работать весь таймаут → параллелизм не даст ускорения.

### 4. Объединение результатов

Два assignment словаря нужно просто объединить:
```python
narrow_assignment = narrow_solver.solve()
wide_assignment = wide_solver.solve()
combined = {**narrow_assignment, **wide_assignment}
```

Коллизий не будет, так как `pallet.id` уникальны.

## Оценка эффективности для S7

Из baseline результата известно:
- **Total:** 3406 паллет
- **Not placed:** 167 (HEIGHT_LIMIT: 103, NARROW_AISLE_MISMATCH: 64)

**NARROW_AISLE_MISMATCH: 64** → это узкопроходные паллеты без подходящих секций.

**Сколько всего узкопроходных паллет?** Нужно проанализировать FloorS7.json. Если там ~70-100 узкопроходных (2-3% от общего), то:

- **Narrow task:** 70-100 паллет × N узкопроходных секций
- **Wide task:** 3300-3336 паллет × M обычных секций

**Проблема:** Wide task остаётся огромной (3300 паллет, ~1400 секций) → агрегация всё равно нужна → время ~180-200s.

**Вывод:** ⚠️ Параллелизм не даст 2× ускорения, потому что wide task доминирует по времени.

## Когда это имеет смысл?

✅ **Хорошо работает если:**
- Узкопроходных паллет ~30-50% (задачи примерно равны)
- `strictNarrowAislePlacement=True` (чёткое разделение)
- `allowReslot=False` или `existing=0` (нет кросс-placement)

❌ **Плохо работает если:**
- Узкопроходных паллет <5% (несбалансированная нагрузка) ← **S7 случай**
- `strictNarrowAislePlacement=false` (нужна гибкость cross-placement)
- `allowReslot=True` с existing паллетами (сложная логика текущих секций)

## Альтернативный подход: Приоритетное размещение

Вместо параллельного решения — **последовательное с приоритетом:**

1. **Этап 1:** Разместить узкопроходные паллеты в узкопроходные секции (маленькая задача, быстро)
2. **Этап 2:** Разместить остальные паллеты в остальные секции (большая задача, используя уже занятые узкопроходные секции)

**Преимущества:**
- Гарантирует размещение узкопроходных паллет в их "родные" секции
- Остальная задача видит реальную занятость
- Последовательность → нет race conditions

**Недостатки:**
- Нет параллелизма
- Суммарное время = time1 + time2 (не max(time1, time2))

---

## Рекомендация для S7

❌ **Не стоит реализовывать параллельное разделение для S7**, потому что:
1. Узкопроходных паллет мало (~2%) → несбалансированная нагрузка
2. Wide task всё равно будет работать ~180s → параллелизм не поможет
3. Текущая агрегация уже эффективно обрабатывает разделение через `narrow_priority_sum` в целевой функции

🎯 **Лучше сфокусироваться на:**
- Оптимизации постобработки (отключить reslot для холодного старта)
- Профилировании текущих узких мест
- Дальнейшем увеличении `_BUCKET_CHUNK_SIZE`

## Но может быть полезно для других сценариев

Если в будущем появятся задачи с ~30-50% узкопроходных паллет, параллельное разделение будет эффективным. Реализация может выглядеть так:

```python
def solve_parallel_narrow_wide(pallets, sections, settings):
    """Параллельное решение для узкопроходных и обычных паллет."""
    narrow_pallets = [p for p in pallets if p.is_narrow]
    wide_pallets = [p for p in pallets if not p.is_narrow]
    
    narrow_sections = [s for s in sections if s.narrow_aisle]
    wide_sections = [s for s in sections if not s.narrow_aisle]
    
    # Два независимых solver
    with ThreadPoolExecutor(max_workers=2) as executor:
        narrow_future = executor.submit(solve_task, narrow_pallets, narrow_sections, settings)
        wide_future = executor.submit(solve_task, wide_pallets, wide_sections, settings)
        
        narrow_assignment = narrow_future.result()
        wide_assignment = wide_future.result()
    
    return {**narrow_assignment, **wide_assignment}
```

**Условие применения:**
```python
narrow_ratio = len(narrow_pallets) / len(pallets)
if 0.3 <= narrow_ratio <= 0.7 and settings.strictNarrowAislePlacement:
    return solve_parallel_narrow_wide(...)
else:
    return solve_unified(...)
```

## Обновление после обнаружения регрессии (2026-07-24)

### Почему идея стала актуальнее

Эксперимент с `BUCKET_CHUNK_SIZE=5` показал:
- **NARROW_AISLE_MISMATCH вырос с 64 до 155** (+91 паллета)
- Узкопроходные паллеты особенно чувствительны к огрублению агрегации
- Смешивание узкопроходных и обычных паллет в одной модели создаёт конфликты

### Реалистичная оценка для S7

**Сценарий:** 200 узкопроходных + 3206 обычных паллет

- **Narrow task:** 200 паллет × 50-100 узкопроходных секций = 10k-20k пар
  - Точная модель (без агрегации): ~5-10 секунд, OPTIMAL
  
- **Wide task:** 3206 паллет × 1430 обычных секций = ~2.5M пар
  - Агрегированная модель: 180s, FEASIBLE

**Итого:** ~3240/3406 за max(10s, 180s) = 180s

**Выигрыш vs baseline:** +1 паллета, -8s, **гарантия оптимального узкопроходного размещения**
