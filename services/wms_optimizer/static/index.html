Обзор

WMS Optimizer — Python-сервис на базе FastAPI, который по снимку текущей занятости склада (occupancy) и списку новых паллет для размещения рассчитывает оптимальный план расстановки с помощью OR-Tools CP-SAT солвера и эвристики FFD (First Fit Decreasing) для тёплого старта. Результат — список операций PUT/MOVE для выполнения в 1С.

Для кого: интеграция с 1С:Предприятие (конфигурация ЕРП, расширение Лико_WMS). Сервис принимает JSON-запросы от модуля Лико_WMS_Сервер и возвращает готовый план размещения.

Быстрый старт

# 1. Поднять сервис через Docker Compose
docker compose up -d wms-optimizer

# 2. Проверить health
curl http://localhost:8010/health

# 3. Отправить запрос на оптимизацию (пример ниже в разделе "Примеры вызова")
curl -X POST http://localhost:8010/api/optimize \
  -H "Content-Type: application/json" \
  -d @request.json

Установка и запуск

Сборка и запуск через Docker Compose

# Из корня репозитория (где docker-compose.yml)
docker compose up -d --build wms-optimizer

# Только пересборка образа
docker compose build wms-optimizer

Порт по умолчанию

8010 — задан в config/settings.json → api.port, проброс в docker-compose.yml: "8010:8010"

Как изменить порт

  1. Отредактировать services/wms_optimizer/config/settings.json: 
    {
  "api": {
    "host": "0.0.0.0",
    "port": 9000,  // ← новый порт
    "workers": 1
  }
}
  2. Либо изменить только проброс в docker-compose.yml (внешний порт): 
    ports:
  - "9000:8010"  # внешний:внутренний
  3. Перезапустить: docker compose up -d --build wms-optimizer

API Endpoints

GET /health

Health check — возвращает {"status": "ok"}

POST /api/optimize

Синхронная оптимизация — возвращает результат сразу (ограничение: timeLimitSeconds из settings, обычно 120 сек)

Request: OptimizationRequest (см. раздел "Схемы данных")

Response: OptimizationResponse — готовый план операций PUT/MOVE, метрики, не размещённые паллеты

POST /api/optimize/async

Асинхронная оптимизация — для больших задач (>1000 паллет). Возвращает {"optimizationId": "...", "status": "RUNNING"} сразу, расчёт идёт в фоне

GET /api/optimization/{id}

Статус асинхронной задачи — RUNNING | COMPLETED | FAILED

GET /api/optimization/{id}/result

Результат завершённой асинхронной задачи (тот же OptimizationResponse)

maxOperations — выбор значения

maxOperations — это лимит количества операций (PUT + MOVE) в результирующем плане размещения.

Правило:

maxOperations ≥ количество новых паллет + (10% от existing для реслота)
Сценарий maxOperations Примечание
Холодный старт 3406 паллет 5000 3406 PUT + ~1594 MOVE (10% реслот)
Инкрементальное 200 паллет 1000 200 PUT + 800 MOVE резерв
Уплотнение (mode=compact) 500 Только MOVE, нет PUT
Тест/debug 300 Минимум, для быстрого прогона

Использование Параметры

OptimizationRequest

Поле Тип Обязательное Описание
optimizationId string ✗ (для async — ✓) UUID запроса
mode "place" | "compact" ✗ (default: "place") place = разместить новые паллеты, compact = уплотнить существующие без новых

OccupancySection — занятость секций (текущее состояние склада)

Occupancy = снимок текущего состояния склада на момент запроса оптимизации. Одна строка = одна секция со всеми её параметрами (размеры, ограничения, правила) и до 3 паллет, которые уже стоят внутри. Источник — Лико_WMS_Сервер.СобратьЗанятостьСекций().

Operation

Операция для выполнения в 1С:

{
  "pallet": "uuid",
  "operation": "PUT",       // PUT = разместить новую | MOVE = переставить существующую
  "oldAddress": null,       // для PUT = null, для MOVE = откуда
  "newAddress": "uuid",     // куда разместить
  "sequence": 1             // порядок выполнения
}

NotPlaced

Паллета, которую не удалось разместить:

{
  "pallet": "uuid",
  "reason": "NARROW_AISLE_MISMATCH",  // причина отказа
  "details": "..."                     // детали
}

Причины отказа: NARROW_AISLE_MISMATCH (узкопроходная паллета, нет узкопроходных секций), HEIGHT_LIMIT, DEPTH_LIMIT, LIFT_LIMIT, MAX_PALLET_SIZE_LIMIT, WEIGHT_LIMIT, NO_SPACE, RESLOT_LIMIT.

Отладка

Отладка сервиса из VS Code с точкой останова

Пошаговый сценарий: вызов из 1С доходит до Python и останавливается на breakpoint в VS Code.

  1. Остановить Docker-контейнер (если запущен): 
    docker compose stop wms-optimizer
  2. Открыть проект services/wms_optimizer/ в VS Code
  3. Создать/обновить .vscode/launch.json: 
    {
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Python: FastAPI",
      "type": "debugpy",
      "request": "launch",
      "module": "uvicorn",
      "args": [
        "main:app",
        "--host", "0.0.0.0",
        "--port", "8010",
        "--reload"
      ],
      "justMyCode": false,
      "cwd": "${workspaceFolder}"
    }
  ]
}
  4. Поставить breakpoint в нужной функции (например, api/routes.py строка 30: async def optimize_sync(...))
  5. Запустить через "Run and Debug" (F5) — сервис поднимется локально с дебаггером
  6. Сделать вызов из 1С (тот же HTTPСоединение("localhost", 8010)) — выполнение остановится на breakpoint, можно смотреть значения переменных (req.occupancy, req.newPallets и т.д.)

Примечание: Remote debug (debugpy attach к контейнеру) не настроен в проекте. Для отладки рекомендуется вариант выше — остановить контейнер, запустить локально с launch.json.

Конфигурация

config/settings.json

Основной конфигурационный файл:

{
  "defaultSettings": {
    "allowReslot": true,
    "maxReslotPercent": 20,
    "maxOperations": 300,
    "timeLimitSeconds": 120
  },
  "api": {
    "host": "0.0.0.0",
    "port": 8010,
    "workers": 1
  },
  "logging": {
    "level": "INFO"
  }
}
  • api.host — адрес для прослушивания (0.0.0.0 = все интерфейсы)
  • api.port — порт сервиса (default 8010)
  • api.workers — количество worker-процессов uvicorn (для production можно увеличить до 2-4)
  • defaultSettings — дефолтные значения OptimizationSettings, если не переданы в запросе

config/weights.json

globalWeights — веса для GlobalScore (метрика итогового результата в ответе API, постпроцессинг, не участвует в самом CP-SAT). localWeights — веса старого scoring-выбора адреса, больше не используются: выбор адреса реализован детерминированным правилом 1С (см. раздел «Выбор адреса»), секция оставлена в файле только для истории/тестов. Редактируются редко — только для fine-tuning globalWeights. См. optimizer/scoring.py.

Переменные окружения

Сервис НЕ использует env-переменные для конфигурации — все настройки в config/settings.json. Для изменения порта/хоста — редактировать JSON напрямую.

Производительность

  • Малая задача (<100 паллет): ~1-5 сек, синхронный режим (/api/optimize)
  • Средняя задача (100-500 паллет): ~10-60 сек, синхронный режим
  • Большая задача (>500 паллет): рекомендуется асинхронный режим (/api/optimize/async), time limit 300-600 сек
  • Стресс-тест (2690 паллет реального склада): ~8-12 мин при timeLimitSeconds=600

Рекомендации: для задач >1000 паллет — всегда async режим + увеличить timeLimitSeconds до 600. Для первого прототипа/теста — allowReslot=false, timeLimitSeconds=30.
