## 2026-07-24 [claude] Лико_WMS_АлгоритмыСервер — BSL-модуль оптимального заполнения секций

**Суть:** Создан новый общий модуль `Лико_WMS_АлгоритмыСервер` с функцией `ОптимальноеЗаполнениеСекции()` — чистый BSL-код для локальной оптимизации заполнения одной секции паллетами. Жадный алгоритм с look-ahead симуляцией и предпочтением гомогенного заполнения (3×900 лучше чем mixed).

**Изменения:**
- `output/Liko_WMS_OptimalSectionFill.bsl` — полный BSL-код модуля (~355 строк)
- `wiki/modules/Лико_WMS_АлгоритмыСервер.md` — страница вики с описанием алгоритма
- `wiki/index.md` — добавлена ссылка на новый модуль, обновлена статистика (404 страницы, 19 Лико_-модулей)
- `wiki/log.md` — эта запись

**Функция:** `ОптимальноеЗаполнениеСекции(Секция, ТаблицаТипов, ЗазорМежду = 50)` → массив `[{ИндексТипа, Количество}]`

**Алгоритм:**
1. Фильтрация допустимых типов (высота/ширина/вес/узкопроходность)
2. Жадный цикл с look-ahead: для каждого слота СИМУЛИРУЕТ заполнение остатка всеми кандидатами
3. Выбор типа с максимальным скором: `количество_паллет × 1000 + утилизация_ширины × 100`
4. Гомогенное заполнение: после первого паллета пытается взять ТОТ ЖЕ тип (3×900 вместо 1×900+1×1200+1×800)
5. Группировка результата: `[тип0, тип0, тип1]` → `[{тип0: 2шт}, {тип1: 1шт}]`

**Отличие от простого жадного:** look-ahead предотвращает локальные максимумы. Пример (секция 2700мм):
- Наивный: 1×1200 → 1×1200 → СТОП (остаток 200мм) = **2 паллеты**
- Look-ahead: 1×900 → 1×900 → 1×800 = **3 паллеты** ✓

**Формула зазоров:** N паллет → (N+1) зазоров по 50мм. Пример: 3 паллеты = |50| п1 |50| п2 |50| п3 |50| = 200мм зазоров.

**Документация:** Обширные русские комментарии в коде — объяснение алгоритма на простых примерах, без технического жаргона.

**Связи:** [[Лико_WMS_АлгоритмыСервер]] [[Лико_WMS_Сервер]] [[Лико_СкладскиеСекции]] [[Лико_ПодобратьЯчейку]] [[wms_optimizer]] [[section_packer]]

**Применение:** Используется при последовательном размещении паллет: `ПодобратьЯчейку()` находит секцию для первого паллета → если секция пустая, запускается `ОптимальноеЗаполнениеСекции()` для выбора оптимальной комбинации из оставшихся паллет → после заполнения секции процесс повторяется.

**Зависимости:** Чистый BSL без внешних библиотек, использует только встроенные конструкции 1С (Массив, Соответствие, Структура, Для/Пока/Цикл).

**Аналог в Python:** `services/wms_optimizer/optimizer/section_packer.py` — функция `optimize_section_fill()` с той же логикой, endpoint `POST /api/pack_section`.

**Суть:** В незакоммиченных правках `ПодобратьЯчейку` (старая версия переименована в `ПодобратьЯчейкуСтар`) получила новое правило в финальном ГДЕ запроса — «монтажный зазор»: если в секции уже 1 паллет, остаток ширины должен быть ≥ ширина_нового_паллета + 150мм; если 2 паллета — +200мм; пустая секция — без доп. зазора. `ОшибкиРазмещенияВАдрес` (вызывается через `ОшибкиРазмещенияПаллетаВАдрес`) это правило не проверяла — прямое нарушение [[СинхронизацияПодборВалидация]]: ручное размещение, проведение `Лико_ПеремещениеПаллета2_0`/`Лико_ЗаданиеНаОтборРазмещение`, дефрагментация и виртуальный симулятор ЗагрузкиСклада пропускали бы размещения без нужного зазора.

**Исправление:** добавлена проверка 13a в `ОшибкиРазмещенияВАдрес` (`Catalogs/Лико_СкладскиеСекции/Ext/ManagerModule.bsl`) — считает `КоличествоПаллетВСекции`/`ОстатокШиринаСекции` из уже полученных `Адрес1/2/3` (работает и с `ВиртуальноеСостояние` без доп. правки) и требует тот же зазор 150/200мм. Подтверждено пользователем как жёсткое физическое ограничение.

**Вне рамок фикса:** legacy-пара `ПодобратьЯчейкуСтар`/`ОшибкиРазмещенияВАдресСтарый` не тронута (без зазора с обеих сторон — уже синхронна); `ПодобратьЯчейкуОперативнаяПамять` — отдельная in-memory реализация, потенциально тоже нуждается в этом правиле, но не входила в исходный запрос — оставлена как наблюдение на будущее.

**Обновлены:** [[Лико_ПодобратьЯчейку]] (параметр `Все`, `ПотенциалПоВесу`, раздел «Финальный фильтр — монтажный зазор»), [[СинхронизацияПодборВалидация]] (таблица синхронизации + пример).

**Страницы:** wiki/services/telegram_voice.md, wiki/extensions/Лико_ГолосовойАссистент.md, wiki/tools/tell-1c.md

### Изменения в telegram_voice (Python)
- `POST /context` — приём контекста из 1С (session_id, chat_id, tools, system_prompt)
- `POST /test-text` — вставка тестового текста без Telegram (для отладки в РФ)
- `GET /latest` — опрос последнего ответа (1С polling каждую секунду)
- `GET /display` — HTML-страница для ПолеHTML с автоопросом
- `session.py` — управление сессиями (chat_id → контекст)
- `llm.py` — OpenRouter клиент с function calling

### Изменения в Лико_ГолосовойАссистент (1С)
- Полный редизайн: WebSocket → HTTP polling
- Кнопка «Спросить AI» — собирает контекст, отправляет POST /context
- Контекст вставляется прямо в JS-переменную CTX (без скрытых div и плейсхолдеров)
- `ИнструментыСклада()` — 3 инструмента для function calling
- `ПолучитьКонтекстАссистента()` — system_prompt + tools для трёх типов
- `ПостроитьHTMLДляФормы()` — генерация HTML с JS polling и контекстом
- Весь код консолидирован в Module.bsl (Лико_АссистентСервер и Лико_АссистентКлиент удалены)

### /tell-1c — Claude-скилл
- Слэш-команда для отправки сообщений в 1С без Telegram
- Write UTF-8 файл + Bash curl (PowerShell портит кириллицу)
- Автодоступ в settings.json — без подтверждений

### Технические детали
- Кодировка: PowerShell `ConvertTo-Json` портит кириллицу → `????`. Решение: Write (UTF-8) + bash curl.
- Docker: `--env-file .env` обязателен (Dockerfile не копирует .env)
- Модель whisper: без volume mount перекачивается при каждом build (~1GB)
